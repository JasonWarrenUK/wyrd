## What we're building

Wyrd's feature roadmap covers everything from the original TUI build-out (capture forms, logging, rituals, documentation assets, compaction — Milestones 3, 5, 6, 7, 8) through to newer work: a spend-tracking depth model built on movement nodes (Milestone G), a status lattice giving every node a kind and stage (Milestone A), expanded node types (Milestone B), backlog/staleness triage (Milestone C), reusable query fragments called skeins (Milestone D), internal tech debt cleanup (Milestone E), and visual polish across the Charm stack (Milestone F).

Milestones 3, 5, 6, 7, and 8 (and part of G) predate this roadmap and were carried over from `docs/roadmaps/archive/tui.md` when that file was superseded; their incomplete tasks live here now, the completed ones are recorded as `done`.

## Milestone sequence and the reasoning behind it

Each milestone's own goal statement (see `wyrd.md`) is authoritative; in short: **M3** wires `huh`-based creation forms to the capture bar. **M5** adds structured logging. **M6** brings the ritual runner into the TUI. **M7** captures screenshots/gifs for documentation once the UI stabilises — hence its heavy cross-milestone dependency footprint (DA.2 alone depends on parts of A, B, C, and F). **M8** handles archived-node compaction. **MG** makes money movements first-class nodes. **MA** is the status lattice underpinning kind/stage on every node — most other milestones (MB, MC, MG) depend on pieces of it. **MB** adds the bookmark node type. **MC** derives blocked/stale status from the graph. **MD** introduces skeins. **ME** is tech-debt cleanup, mostly independent. **MF** is visual polish, largely independent but gates the M7 documentation captures.

## Decisions that shaped the structure

- **Terminal milestone edges**: a milestone's Mermaid node is a sink for its own leaf tasks (`{leaf} --> M{N}`) and a source for anything that depends on the whole milestone (`M{N} --> {task}`) — this replaced the old fan-out convention (`mDL --> DL1 & DL2 & ...`) during migration.
- **Carried-over external references**: two prose dependencies from the pre-migration file (`VS.10`, `NV.8`) point at tasks that only exist in the archived `tui.md`, not in this file. Both are marked done there, so they impose no blocking status; they were dropped from the machine-readable `dependsOn` graph but the original task descriptions still mention them in prose where relevant (`DA.1`, `DA.2`, `DA.7`).
- **DL.6 added post-migration**: implementing DL.1 (`isBlocked` computed property) surfaced a structural gap — the query engine only holds a `GraphIndex`, with no access to the Kind/StageGroup registries `isBlocked` needs to resolve stage terminality, and the two CLI query paths never built those registries at all (only the TUI path did). Rather than fold that wiring silently into DL.1, it's tracked as its own task (DL.6) and DL.1 now depends on it — keeping the dependency graph honest about what DL.1 actually needs before it can ship.
