wyrd

wyrd /wɪərd/ n. Old English: fate, destiny; that which has come to pass. The root of weird, by way of the Weird Sisters.

Wyrd is a personal organiser built as a flat-file property graph. Every task, note, journal entry and budget is a JSONC file on disk; every relationship between them is another. A single Go binary builds a live in-memory index over the lot, lets you query it with Cypher, and wraps the whole thing in a terminal UI. Sync is git. Delete the binary and your data is still just files.

The shape of the thing

Files at the bottom, a graph in the middle, a terminal on top

The store writes atomically (temp file, then rename) and an fsnotify watcher keeps the index live, so a node edited in your text editor appears in the TUI immediately. Every layer talks to the next through an interface seam (StoreFS, GraphIndex, QueryRunner), which is what keeps a filesystem-backed graph testable. Nodes are never deleted; archival is a status. Edges, being cheap, genuinely die.

Queries are Cypher, deliberately A read-only subset of Neo4j's query language, parsed with Participle. Date variables like $today + 7d and UNION are in; mutations are rejected at the gate.

The working loom

Briefly, because the interesting part is what comes next: the core is live and in daily use.

Capture & editing

Prefix-triggered creation forms, ctrl+o to edit any node in place, edge management from within the form. A recent fix made edits merge into a clone of the original node, so nothing a form doesn't own can be lost.

Rituals

Scripted workflows: sequences of prompts, queries, and gate steps that run on startup or on demand. A morning review that asks questions and writes the answers into the graph.

Budgets

Envelope budgets as nodes, dated spend entries, warn thresholds, and progress bars in a budget view. Currently an embedded spend log; about to become something better (see thread II).

Observability

Structured logging throughout via charmbracelet/log, with a :log palette command that tails the log file in an overlay without leaving the TUI.

Views & theming

Saved Cypher views drive the dashboard panes. Themes are JSONC files; the default palette is called Cairn. A command palette and split-pane keyboard model hold it together.

Tools of the trade

Standing on Charm

Nearly all of the TUI rests on the Charm stack, which is most of the reason a one-person side project can afford this level of finish: each library does one thing, and they compose. The non-Charm load-bearers get a mention in the footer (Participle parses the Cypher; Cobra runs the CLI; fsnotify keeps the index honest).

Where it's weaving

Four threads worth watching

The roadmap runs to 96 tasks across 12 milestones, but most of it hangs off four design ideas. Each one trades a stored fact for a derived one, or a special case for a shape.

I

The status lattice

Milestone A · in progress

Every node has a kind — Task, Habit, Event, Project, and yes, Goblin ships as a default — and every kind references a stage group: a named progression like Open → Maybe → Later → Soon → Now → Done. Groups define their own cycle behaviour: habits loop back to the start, projects terminate, and a group can loop to a named stage rather than the first.

What remains is the configurability: kind selection inside the create and edit forms, user-defined kinds and stage groups written from the TUI itself, and the genuinely thorny bit: when a kind moves to a different stage group, existing nodes may hold a stage that no longer exists. The answer is a remap prompt that asks where each orphaned stage should land, defaulting to a name match. Until you answer, those nodes are simply left untouched.

Done is a stage, and a stage is yours to define.
II

Money as topology

Milestone G · Spend Depth · next up

A spend, an income, and a transfer become the same thing: a movement node, dated, staged (expected → cleared), carrying an amount. What distinguishes them is the shape of their edges to budget categories:

draws_from adds_to meaning
edge none a spend
none edge an income
edge edge a transfer

There is no type field to keep in sync, and the unbalanced transfer is unrepresentable by construction: one node, both edges, created together. The stage field (expected → cleared) then unlocks the second idea: bottom-up budgeting, which inverts where an envelope's number comes from.

Top-down · today

The envelope as aspiration

You decide groceries deserves £200, write it down, and spend the month negotiating with a number you invented. When reality disagrees, the budget is the thing that bends.

Bottom-up · planned

The envelope as forecast

The allocation derives from the sum of expected movements in the coming period: the standing order, the insurance renewal, the birthday that will not move. Explicit allocations stay possible; derived ones are visually distinguished in the TUI.

III

The calm dashboard

Milestone C · Backlog

Blocked status is never stored. A node is blocked if anything pointing at it through a blocks edge sits at a non-terminal stage; the query engine computes n.isBlocked on the fly, so the flag cannot go stale. Staleness itself gets a muted badge once a node has sat idle past a threshold (fourteen days by default).

The piece worth stealing is the calmness threshold: when the count of active-stage nodes drops below N, the dashboard quietly appends a triage section holding the M most pressing backlog items plus one serendipitous pick. The backlog only knocks when you have room to answer the door.

IV

Skeins

Milestone D · query composition

A skein is a named fragment of Cypher — a WHERE clause, an ORDER BY, a RETURN projection — stored as a JSONC file like everything else in the store. Saved views reference skeins by name; the engine interpolates them at parse time, and a circular reference is a parse error rather than a runtime surprise. Query logic becomes something you compose and reuse, with the same file-watching liveness as the data it queries.

A skein, fittingly, is a length of yarn wound for use.

The finishing pass

Nine tasks of pure finish, drawn from a survey of what the Charm stack can do. None of them touches the data model; together they close the gap between a TUI that works and one that feels considered.
